# История изменений

## 0.7.0 — 2026-11-23

- **Новое: замена картинок элементов** (`PREVIEW_PICTURE`, `DETAIL_PICTURE`) через `element_update` и `element_create`.
  Источник: `{"url": "https://…"}` или `{"base64": "…", "name": "photo.jpg"}`. Тип определяется по содержимому (JPEG, PNG, WebP, GIF), лимит 10 МБ,
  имя файла очищается, расширение ставится по реальному типу. Старый файл заменяется (удалить картинку нельзя).
- Загрузка по url: только HTTPS на порт 443, только публичные IP (адрес закрепляется, переадресации проверяются заново), чтобы сервер нельзя было
  использовать для обращения во внутреннюю сеть.
- `element_get` теперь возвращает `preview_picture` и `detail_picture` (id, адрес, имя, размеры) или `null`.
- В ответе и журнале событий вместо содержимого файла только описание (имя, тип, размер, габариты).
- 213 автотестов. Слой Битрикса (`CFile::MakeFileArray`) нужно проверить на живом сайте: см. docs/VERIFY-ON-SITE.md.

## 0.6.0 — 2026-11-22

- **Новое: подключение по коду (OAuth Device Authorization Grant, RFC 8628)**, как `gh auth login`. Адреса: `POST /site.ops/oauth/device` (старт),
  `/site.ops/oauth/token` с `grant_type=urn:ietf:params:oauth:grant-type:device_code` (опрос), страница подтверждения `/site.ops/oauth/verify/` (вход администратором,
  сверка кода, «Разрешить» / «Отклонить»). Стандартные ответы опроса: `authorization_pending`, `slow_down`, `expired_token`, `access_denied`.
  Выдаются те же токены (доступ 1 час, обновление 30 суток), права определяются настройками сайта. Код устройства и код для человека хранятся только как SHA-256.
- Клиент `tools/device_login.py` (`login`, `token`), токены в файле с правами 600.
- Регистрация клиентов принимает `grant_types` с device_code без `redirect_uris`. Документ сервера объявляет `device_authorization_endpoint`.
- Новая таблица `orgbox_siteops_oauth_device` создаётся сама при первом обращении. Обновление `.htaccess` обязательно (новые адреса `device`, `verify`): кнопка обновления его заменяет.
- 203 автотеста.

## 0.5.4 — 2026-11-21

- **Исправлено: кнопки «Проверить обновления» и «Установить» на странице настроек не работали** (ошибка «Argument #4 ($profile) must be of type PackageProfile»):
  страница создавала `Updater` без профиля пакета. Сборка обновления вынесена в `Bootstrap::updater()`.
  **Обновление с 0.5.2 и ниже на 0.5.4 нужно один раз сделать вручную** (docs/UPDATES.md); дальше работает кнопка.
- Страница настроек покрыта тестами во всех сценариях: проверка и установка обновления (с подписью, без подписи, чужая подпись, ошибка сети,
  установка без проверки), список OAuth-подключений и их отзыв. 187 автотестов.

## 0.5.3 — 2026-11-20

- **Исправлено (найдено на живом сайте): названия, коды и тексты элементов читались экранированными** (`&lt;p&gt;` вместо `<p>`, `&amp;` вместо `&`),
  потому что для чтения использовался `GetNext` без исходных значений. Теперь берутся исходные значения (`~ПОЛЕ`). Без этого запись изменённого текста
  привела бы к двойному экранированию. Первое подключение к настоящему Битриксу: чтение инфоблоков, разделов, элементов и свойств проверено.
- 175 автотестов.

## 0.5.2 — 2026-11-19

- **Исправлено: страница согласия OAuth падала целиком** (общая страница ошибки Битрикса). Административные файлы Битрикса
  (`prolog_admin_after.php`, `epilog_admin.php`) подключались из функции, а им нужны глобальные переменные админки.
  Теперь страница согласия только принимает решение, а вывод и подключение пролога идут на верхнем уровне файла.
- Новый тест запускает страницы в отдельном процессе на верхнем уровне с «капризными» файлами пролога, как у настоящего Битрикса;
  на прежнем коде он воспроизводит эту ошибку.
- 174 автотеста.

## 0.5.1 — 2026-11-18

- **Исправлено: на странице настроек не работали «Сохранить» и «Создать токен»** («Не прошла проверка сессии Битрикса»): штатная проверка
  `check_bitrix_sessid` на странице `site.ops` не проходила. Добавлена собственная защита форм от подделки запросов (CSRF), не зависящая от сессии PHP:
  cookie `SameSite=Strict` на пути `/site.ops/` и HMAC в скрытом поле. Штатный sessid остаётся запасным вариантом. Так же защищена страница согласия OAuth.
- При отказе страницы сообщение перечисляет, что именно не пришло (sessid, cookie сессии, cookie и поле защиты форм).
- Страница согласия OAuth покрыта тестами (выдача и отказ, подделка запроса, экранирование имени клиента, чужой `redirect_uri`).
- 172 автотеста.

## 0.5.0 — 2026-11-17

- **Исправлено: настройки со страницы администратора не доходили до публичной части.** В 0.4.0 они хранились в `b_option` «по сайту» через
  `SITE_ID`, а в админке и на публичных страницах он может различаться; галочки могли не сохраняться или не действовать.
  Теперь для `site.ops` настройки лежат в файле `site.ops/_data/settings.php` внутри папки сайта; таблицы OAuth различают сайты по ключу от пути корня.
  Обновление и резервные копии эту папку не трогают, сборка не пропускает её в архивы.
- Страница настроек говорит вслух: не прошла проверка сессии, запись невозможна, значения не сохранились (проверка чтением после записи);
  показывает путь к файлу настроек и можно ли в него писать.
- Убран старый подписанный API (HMAC) и его точка входа `/site.ops/api`: включить его на странице настроек было нельзя.
  При ручном обновлении удалите папки `site.ops/lib` и `site.ops/api` перед распаковкой (см. docs/UPDATES.md).
- Новый документ docs/QUICKSTART.md: что делать после установки.
- 156 автотестов (страница настроек теперь покрыта), 49 проверок на настоящем Apache.

## 0.4.0 — 2026-11-16

- **Подключение по ссылке (OAuth 2.1):** код авторизации + PKCE (S256), динамическая регистрация клиентов (RFC 7591), документы обнаружения
  (RFC 8414, RFC 9728), токены с ротацией и обнаружением повторного использования, отзыв (RFC 7009), страница согласия администратора
  Битрикса, список и отзыв подключений на странице настроек. Только форма `site.ops`. Не проверялось с живыми клиентами Claude.
- **Адреса без `.php`:** точки входа переехали в папки; MCP — `/site.ops/mcp`, настройки — `/site.ops/admin/`, подписанный API — `/site.ops/api`.
  `.htaccess` отключает редирект на папку со слэшем (он ломает POST) и передаёт заголовок `Authorization`.
- Закрытие от браузера исправлено: `FilesMatch` в корне открыл бы `index.php` в копиях `_updates`; теперь доступ выдают `.htaccess` папок точек входа.
- Проверка `.htaccess` на настоящем Apache: `tests/apache/verify.sh` (46 проверок), запускается в CI.
- Для автообновления проверяется минимальный набор файлов, чтобы смена раскладки не блокировала обновление.
- **Обновление с 0.3.x вручную** (см. docs/UPDATES.md): старый установщик отклонит новую раскладку.
- 144 автотеста.

## 0.3.0 — 2026-11-15

- Новая форма установки: **папка `site.ops`** в корне сайта (без регистрации модуля в `local/` и `bitrix/`). Рекомендуется для
  нескольких сайтов на одном Битриксе и для хостингов с симлинками.
- В этой форме токен и настройки **отдельные для каждого сайта** (по `SITE_ID`); служебные файлы закрыты `.htaccess`.
- Релиз теперь содержит два архива: `site.ops-X.Y.Z.zip` и `orgbox.siteops-X.Y.Z.zip`; обновление берёт архив своей формы.
- Рабочая папка обновлений внутри `site.ops/_updates` исключена из копирования и удаления.
- Страница настроек вынесена в общее представление для обеих форм.
- 106 автотестов.
